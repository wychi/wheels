# MI300X — AMD CDNA3 (gfx942)

> Status: **high-effort fork.** utlx wheel does not currently support ROCm/AMD; enabling MI300 requires either a wheel fork or abandoning uTLX features in favor of plain ROCm Triton.

## Hardware specs (verified)

| Spec | Value |
|---|---|
| Peak bf16 Matrix TF/s | 1,307 |
| Peak fp8 Matrix TF/s | 2,614 |
| HBM3 bandwidth | 5.3 TB/s |
| L2 / Infinity Cache | **256 MB total** (chip-wide, shared across all 8 XCDs — *not* per-CU) |
| LDS / CU (binding constraint) | 64 KB |
| VGPR / wave64 | 256 |
| CUs / XCDs | 304 / 8 |
| Matrix Core | MFMA `f32_16x16x16_bf16`, `f32_32x32x8_bf16` |
| TDP | 750 W — comfortable, no throttle concern |

| Region | FLOPs | Bytes | Peak ms | Realistic (60–75%) ms |

The 256 MB Infinity Cache is large enough to hold the full working set (~268 MB activations in bf16) for `B=1, S=1024` — plan to land hot tensors there and avoid HBM round-trips. This is the one architecture where the optimistic "1.2 GB fused" S1 IO estimate may genuinely hold (vs H100, where it didn't).

## Tile sizing recipe (64 KB LDS/CU is binding!)

**Einsum tile (BLOCK_M × BLOCK_N × BLOCK_K = 128 × 128 × 32):**
- A: `128 × 32 × bf16 = 8 KB`; B: `128 × 32 × bf16 = 8 KB`.
- `num_stages=2` double-buffer: `(8 + 8) × 2 = 32 KB` LDS. Comfortable inside 64 KB.
- `num_warps=4` with **wave64** (default), MFMA `f32_32x32x8_bf16`.
- `waves_per_eu=2` for occupancy.
- **wave32 alternative**: doubles waves/CU from 4 to 8, may give 5–10% throughput on this shape — worth A/B testing once functional.

**B+C-fused projection tile:**
- 16×16 fused intermediate would need ~128 KB (2× the LDS budget). **Cannot fit on MI300.** Shrinking to 8×8 reduces useful parallelism below the break-even point. **Skip B+C fusion on MI300.**

## Specialization opportunities
- **hipBLASLt for S1 projections** — analogous to cuBLASLt-on-A100. Expect 70–80% of peak.
- **Note**: hipBLASLt has no Cauchy-input safeguards either; the bf16 vs fp8 decision is the same as NVIDIA chips — stay on bf16.
- 256 MB Infinity Cache hits the entire working set — bias toward designs that keep producers and consumers in the same XCD if possible (cache-locality, not just bandwidth).

## Portability concerns
- **utlx wheel is NVIDIA-only.** MI300 enablement requires either (a) a non-trivial fork of the wheel against ROCm Triton, or (b) abandoning uTLX and writing the kernel in plain ROCm Triton (no warp-spec, no TMA equivalents — matrix-core MFMA + LDS swizzle). Either way, **MI300 is not viable for the current submission without ecosystem work**.
- Triton-AMD backend is more mature than uTLX-AMD but still trails NVIDIA Triton; expect rougher autotune and worse numerics on edge cases.

## Top-3 recommendations
1. Use **hipBLASLt for S1 + S3 projections**; write the einsum in plain ROCm Triton (drop uTLX-specific features).
2. Tile einsum **128×128×32, num_stages=2, num_warps=4, wave64** (try wave32 as a tuning knob); skip B+C fusion.
3. End-to-end realistic estimate: **~1.0–1.3 ms**, contingent on writing a separate ROCm path. Submission-only effort: **medium-to-high**.
